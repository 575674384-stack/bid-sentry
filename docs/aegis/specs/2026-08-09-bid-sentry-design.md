# Bid Sentry 产品与架构设计规格

日期：2026-08-09

状态：已确认，M0–M1 发布验证中

适用范围：首个可发布版本及其三个功能里程碑

## 1. 项目摘要

Bid Sentry 是面向投标文件制作场景的开源单机桌面工具。它在用户本机完成文件读取、解析、元数据安全重置、规则检查、模板提取和 DOCX 生成；需要语义理解时，调用用户自行配置的 OpenAI 兼容接口。项目不提供账号系统、中心服务器或文件托管服务。

最终产品包含三项能力：

1. 将 DOCX/PDF 中可能暴露制作环境或制作者身份的元数据重置为非空随机值，并证明正文和版式未被改变。
2. 对照招标文件检查投标文件中的主体名称、固定参数、缺漏项和矛盾项，并为每个问题提供可定位的证据。
3. 从招标文件自带的投标文件格式模板中提取用户确认的资格标模板，填入固定值和企业表单信息，用占位符标记证照、图片和签章位置，生成可编辑 DOCX。

## 2. 已确认的产品决策

- 产品始终为开源单机工具，不建设服务端、账号、订阅或云端文件存储。
- 支持 Windows 和 Linux，使用 Electron 打包。
- 用户自行配置 AI Base URL、API Key 和模型名称。
- 首版只支持 OpenAI 兼容接口；其他协议以后通过独立适配器增加。
- 文档处理在本地完成。发送给 AI 的内容仅限完成当前任务所需的提取文本和结构化上下文。
- 三项能力按里程碑逐步交付，每个里程碑均需达到可运行、可测试、可发布状态。
- OCR 暂不支持。扫描 PDF 可做元数据清洗，但不能进入内容审查或模板制作流程。
- 资格标输出为可编辑 DOCX。DOCX 来源模板以保真提取为目标；PDF 来源模板只保证结构化重建，不承诺像素级一致。
- 模板识别后必须由用户确认范围，程序不能静默选择模板。
- 原文件永远只读，输出使用新文件名；数字签名、加密、损坏或无法安全验证的文件不得修改。

## 3. 目标、成功证据与非目标

### 3.1 目标

- 降低投标文件因隐藏元数据、主体名称混用、固定参数不一致或模板填写错误而产生的风险。
- 让所有自动修改都可解释、可预览、可验证、可撤销。
- 让非技术用户在单机应用中完成从文件选择到报告或成品 DOCX 的完整流程。
- 保持代码边界清晰，使开源贡献者可以独立测试文档、规则、AI 和界面模块。

### 3.2 成功证据

- 元数据清洗前后，指定元数据已被替换为非空随机值，未授权的文档内容部件保持一致，输出文件能被重新解析。
- 审查结果中的每个问题都包含严重级别、问题说明、招标依据、投标证据、位置和建议；没有证据的问题不得显示为确定性错误。
- 资格标生成必须经过“模板确认”和“填充计划确认”，输出 DOCX 可以继续编辑，固定条款未被 AI 改写。
- Windows 与 Linux 的打包产物均通过安装、启动、基础任务和升级兼容性测试。

### 3.3 非目标

- 不判断投标行为是否合法，也不承诺替代律师、招标代理或人工复核。
- 不提供围标、串标或规避监管检测的内容生成能力；元数据功能定位为隐私保护和误关联风险控制。
- 不破解密码、不移除数字签名、不绕过文档权限。
- 首期不支持 OCR、扫描件内容审查、DOC、DOCM、WPS 私有格式或图像文字识别。
- 不承诺将任意 PDF 无损转换成可编辑 DOCX。
- 不自动提交、上传或发送最终投标文件。

## 4. 用户工作流

### 4.1 元数据安全重置

1. 用户选择一个或多个 DOCX/PDF 文件和输出目录。
2. 应用执行类型、大小、加密、签名和结构安全检查。
3. 应用扫描可处理元数据，生成“将要修改的字段类别”预览；预览不回显原敏感值。
4. 用户确认后，后台任务在临时副本上生成随机映射并实施修改。
5. 应用重新打开输出文件并执行内容不变验证。
6. 验证通过后原子写入 `<原名>_sanitized.<扩展名>`，同时输出 JSON 和可阅读的 HTML 报告。
7. 任何强制验证失败都删除未完成临时文件，并保留原文件不变。

### 4.2 招投标文件对照审查

1. 用户分别选择招标文件和投标文件。
2. 应用检测是否有可用文本层；扫描 PDF 明确提示暂不支持。
3. 本地解析器建立带页码、章节、段落、表格和单元格位置的统一文档模型。
4. 确定性规则先检查主体名称、数字、日期、单位、空字段、必填章节和明显冲突。
5. AI 从招标文件提取“要求台账”，从投标文件提取“响应台账”，并返回结构化对照结果。
6. 本地规则引擎合并、去重和验证 AI 结果；无法定位到原文证据的结果降级为“需要人工复核”。
7. 用户按严重级别、章节和问题类型查看结果，并可跳转到双方证据位置。
8. 应用导出 HTML/JSON 审查报告；首期不自动修改投标文件。

### 4.3 资格标预制作

1. 用户选择招标文件，并填写项目和投标单位基础信息。
2. 应用从目录、标题和正文结构中识别“投标文件格式”“资格审查文件格式”等模板候选区段。
3. 用户在模板确认页查看章节、页码或段落范围，选择资格标所需模板。
4. AI 将模板中的项目分为：招标固定值、用户表单值、需上传的图片/证照/签章、需要用户判断的未知项。
5. 应用形成结构化填充计划。固定值必须带招标文件证据，未知项不能由 AI 猜测。
6. 用户确认填充计划并补齐必要信息。
7. 本地生成引擎从原模板提取副本并填值；图片、证照和签章位置插入醒目的可替换占位符。
8. 应用验证模板固定文本、关键参数和结构未被意外改变，然后输出可编辑 DOCX 和制作报告。

## 5. 元数据策略

### 5.1 随机映射原则

- 使用操作系统加密安全随机源，每个输出文件生成独立随机种子和随机映射；种子不写入报告。
- 原值不得复制到日志、报告或遥测数据。
- 同一文件内相同原身份映射到相同随机别名，不同原身份映射到不同别名，以保持内部引用一致性。
- 人员名称使用 `User-<随机标识>`，缩写使用随机大写字母，组织名称使用 `Org-<随机标识>`，文档标识使用随机 UUID。
- 时间使用合法、非未来的随机时间，并保持创建时间不晚于修改时间；不能安全重置的时间字段只报告、不修改。
- 描述类字段使用带随机标识的中性非空值，不生成真实企业或个人名称。

### 5.2 DOCX 处理范围

- Core Properties：creator、lastModifiedBy、created、modified、revision、identifier、title、subject、keywords、category、description、contentStatus、lastPrinted。
- Extended Properties：Company、Manager、Application、AppVersion、Template、TotalTime 等可能暴露制作环境的属性；页数、字数等内容统计值不得随机化。
- Custom Properties：按字符串、数字、布尔和时间类型生成同类型随机值，不删除属性定义。
- 评论与修订记录中的 author、initials、date 等身份属性可以随机化，但评论正文、修订内容和接受状态保持不变。
- 不处理 DOCM；不执行宏；不移除外部链接或嵌入对象，只在报告中提示其存在。

### 5.3 PDF 处理范围

- Info Dictionary 中的 Author、Creator、Producer、CreationDate、ModDate、Title、Subject、Keywords、Trapped。
- XMP 中与上述字段对应的 Dublin Core、PDF、XMP 和应用标识属性。
- 文档 Trailer ID 生成新的随机 ID。
- 页面对象、内容流、字体、图片、注释和附件均不得改变。
- 检测到任意数字签名字段或加密时拒绝处理，不提供强制继续选项。

## 6. 审查模型与规则

### 6.1 统一文档模型

解析器将 DOCX 和带文本层的 PDF 转换为只读结构：

- `DocumentSnapshot`：文件类型、哈希、页数、基础安全特征。
- `DocumentNode`：标题、段落、表格、单元格、列表项、页眉页脚及其层级关系。
- `SourceAnchor`：文件角色、页码、章节路径、段落或单元格标识、原文片段。
- `ExtractedEntity`：主体名称、项目名称、标段、工期、日期、金额、保证金、有效期、人员和资格要求。

### 6.2 确定性规则优先

首批规则至少包含：

- 投标文件出现两个及以上疑似投标单位名称。
- 招标人与投标人角色名称混淆。
- 项目名称、项目编号、标段名称或标段编号不一致。
- 工期、服务期、交货期、投标有效期、保证金、质量标准等固定参数不一致。
- 同一参数在投标文件内部出现相互矛盾的值。
- 模板中的空白、占位符、示例文字或未替换提示仍然存在。
- 要求台账中的必填章节或附件在投标文件中没有可定位响应。

规则输出和 AI 输出统一为 `ReviewFinding`：唯一标识、类型、严重级别、置信度、说明、招标证据、投标证据、建议和来源。来源必须标记为 `rule`、`ai` 或 `combined`。

### 6.3 AI 使用约束

- 文档文本始终视为不可信数据；其中要求模型改变系统规则、泄露密钥或执行外部操作的文字一律视为提示词注入内容。
- AI 只能返回符合版本化 Zod Schema 的 JSON 数据，不能返回可执行代码或文件修改指令。
- AI 不得猜测招标文件未提供的固定值。缺失信息必须返回 `unknown` 和原因。
- AI 结果必须引用输入上下文中的锚点；本地程序验证引用存在后才可提升为问题。
- 不支持结构化输出的兼容接口可返回纯 JSON 文本，但仍须经过同一 Schema 校验；校验失败只允许一次纠正请求，之后任务以可解释错误结束。
- API 请求和错误日志不得包含 API Key；默认日志不记录文档正文。

## 7. 模板提取与生成规则

### 7.1 模板来源优先级

1. DOCX 中用户确认的原始模板区段。
2. PDF 中用户确认的带文本层模板区段，经结构化重建为 DOCX。
3. 不允许 AI 在没有招标模板依据时自由创作资格标版式。

### 7.2 DOCX 保真策略

- 复制原 DOCX 包作为工作副本，只保留用户确认的正文区段。
- 保留被选区段依赖的样式、编号、主题、字体、图片、关系、页眉、页脚和分节属性。
- 不重新创建可直接复用的段落或表格，避免格式漂移。
- 填值操作以明确的文本节点、内容控件、书签或表格单元格为目标；目标不唯一时要求用户确认。
- 固定文本在生成前后进行规范化哈希比对；只有已批准的填充目标允许发生变化。

### 7.3 PDF 重建策略

- 使用页码、坐标、字体和文本块建立阅读顺序及表格候选结构。
- 生成接近原结构的 DOCX，保留标题层级、段落、表格和分页提示。
- 输出前明确展示“PDF 重建结果可能存在版式差异”，并要求用户预览确认。
- 若文本层缺失、顺序严重错乱或无法可靠确定模板边界，则停止生成，不以猜测结果继续。

### 7.4 填充计划

每个 `FieldAction` 包含目标锚点、字段类别、当前文本、建议值、值来源、招标证据、置信度和是否需用户确认。值来源只能是：

- `tender-fixed`：来自招标文件的不可修改值。
- `user-form`：来自用户填写的投标单位或项目表单。
- `placeholder`：需要用户插入图片、证照、签章或其他附件。
- `unknown`：信息不足，必须由用户判断。

占位符统一采用醒目但可编辑的格式，例如 `【请插入：营业执照复印件】`，不得伪造证照、签名或印章。

## 8. 软件架构

### 8.1 技术栈

- Electron、React、TypeScript、Vite。
- pnpm 管理依赖和脚本。
- Zod 作为 IPC、任务文件、AI 输出和报告数据的运行时 Schema。
- Vitest 执行单元和集成测试，Playwright 执行桌面端关键流程测试。
- electron-builder 生成 Windows 与 Linux 发布产物。

文档 ZIP/XML 与 PDF 库必须封装在内部适配器之后。每个适配器在采用前均需通过包含复杂表格、页眉页脚、修订记录、XMP、签名和异常结构的兼容性样例测试；上层领域模型不依赖具体第三方库。

### 8.2 进程边界

- `renderer`：界面和用户确认，不访问 Node API、文件系统或密钥。
- `preload`：暴露最小、版本化、Schema 校验的 IPC 白名单。
- Preload 生产产物固定为 bundled CommonJS `out/preload/index.cjs`：除 Electron 内建模块外不得留下运行时外部依赖或 `require`；Main 只加载该产物，并保持 Renderer sandbox。原因与被否决路径见 `docs/aegis/adr/ADR-0002-sandboxed-bundled-commonjs-preload.md`。
- `main`：窗口、文件选择、任务生命周期、设置、安全存储和 AI 网络请求。
- `worker`：CPU 密集或可能失败的文档解析、转换、清洗和验证。
- `core/documents`：文档格式与安全处理的唯一所有者。
- `core/review`：规则、要求台账和问题合并的唯一所有者。
- `core/generation`：模板候选、填充计划和 DOCX 生成的唯一所有者。
- `core/ai`：OpenAI 兼容协议和模型能力检测的唯一所有者。
- `shared/contracts`：跨进程和跨模块数据契约的唯一所有者。

首期保持单仓库、单桌面应用，不拆分微服务或可独立发布的 npm 包。

### 8.3 任务数据流

1. Main 创建任务 ID 和只读输入快照，包括规范路径、大小、类型和哈希。
2. Worker 解析文件并返回结构化数据，不向 Renderer 暴露任意本机路径操作能力。
3. 需要 AI 时，由 Main 根据任务类型构造最小上下文并发出 HTTPS 请求。
4. 结构化 AI 结果通过 Schema 和引用校验后进入预览。
5. 用户确认的计划交给本地确定性引擎执行。
6. 输出通过重新解析、结构检查和内容不变检查后，以原子重命名方式落盘。
7. 临时文件在成功、失败或取消后清理；崩溃遗留文件在下次启动时由受限清理器处理。

### 8.4 本地设置与密钥

- 普通设置保存在 Electron 应用数据目录的版本化配置文件中。
- API Key 使用 Electron `safeStorage` 加密；操作系统无法提供安全存储时只允许会话级使用，不以明文持久化。
- 不引入数据库。报告随用户选择的输出目录保存，应用不长期保存文档正文或任务历史。
- Base URL 默认要求 HTTPS；仅环回地址可在明确警告后使用 HTTP。

### 8.5 Electron 安全设置

- `contextIsolation: true`、`nodeIntegration: false`、Renderer sandbox 开启。
- 内容安全策略禁止任意脚本、任意导航和 Renderer 直接网络访问。
- 文件路径只能来自系统文件选择器或受校验的任务状态。
- 禁止加载远程页面到拥有 Preload 权限的窗口。
- IPC 的请求和响应均做大小限制、类型校验和任务归属校验。

## 9. 文件安全与失败处理

- 永不覆盖输入文件；输出冲突时由用户选择新名称，不自动覆盖。
- DOCX ZIP 解析限制总展开大小、压缩比、条目数和路径穿越，拒绝 ZIP bomb 与非法路径。
- PDF 解析限制文件大小、页数、对象深度和可提取文本量，超过限制时给出明确原因。
- 文件在任务期间发生修改时，输入哈希检查失败并停止任务。
- 取消任务时终止 Worker 和网络请求，删除未完成输出。
- AI 超时、限流、余额不足、模型不兼容和 Schema 失败分别显示可操作错误，不统一显示为“分析失败”。
- 处理报告不记录原敏感元数据、API Key、完整正文或未经用户选择的本机路径。
- 应用不提供“忽略验证并保存”选项。

## 10. 报告与可解释性

每个任务生成版本化 JSON 报告；面向用户的 HTML 报告由相同数据渲染，避免两个事实来源。

报告包含：应用版本、报告 Schema 版本、任务类型、输入文件指纹、输出文件指纹、执行时间、处理字段类别、规则/模型版本、问题证据、警告、验证结果和最终状态。元数据清洗报告只记录字段名与处理状态，不保存字段原值或随机后的具体值。

所有 AI 问题都显式标记“AI 辅助结果，请人工复核”。确定性规则与 AI 结果在界面和报告中使用不同来源标识。

## 11. 里程碑与交付边界

### M0：桌面基础设施

- Electron 安全骨架、设置页、OpenAI 兼容接口测试、任务框架、日志脱敏、Windows/Linux 构建和基础自动化测试。

### M1：元数据安全重置

- DOCX/PDF 安全检测、随机计划、预览、清洗、内容不变验证、输出与报告。
- 单文件和批量处理均可完成。

### M2：招投标文件对照审查

- DOCX/文本 PDF 统一文档模型、基础要求台账、首批确定性规则、AI 对照、证据定位与报告。
- 不包含自动修复、OCR 或扫描 PDF。

### M3：资格标预制作

- 模板候选识别与确认、动态企业表单、填充计划、DOCX 保真提取、PDF 结构重建、占位符和生成验证。

### M4：发布完善

- Windows x64 与 Linux x64 安装包、升级兼容性、示例文件、用户文档、贡献指南和发布检查。

各里程碑在自身验收通过后才能进入下一个里程碑；M4 的基础构建验证从 M0 开始持续运行，不在最后一次性补做。

## 12. 测试与验收

### 12.1 测试层次

- 单元测试：随机映射、字段分类、规则、Schema、路径安全和错误映射。
- 格式夹具测试：合成 DOCX/PDF，覆盖表格、分节、页眉页脚、评论、修订、XMP、附件、签名、加密和畸形结构。
- 黄金文件测试：比较规范化 OOXML 部件、PDF 页面对象和生成文档结构。
- AI 契约测试：使用固定响应验证结构化输出、锚点校验、注入文本隔离和失败重试。
- 集成测试：从文件选择后的任务输入到报告/输出文件，不调用真实付费 API。
- 桌面端端到端测试：Windows/Linux 的配置、取消、错误提示、清洗、审查和生成关键路径。
- 手工兼容性测试：使用合法脱敏的真实结构样例在 Microsoft Word、LibreOffice 和主流 PDF 阅读器中打开。

### 12.2 M1 强制验收

- 原文件字节不变且修改时间不被应用主动触碰。
- 清洗字段均为合法非空随机值，报告不包含原值。
- DOCX 除批准的元数据/身份属性外，其余包部件规范化哈希一致。
- PDF 页面数量、尺寸、内容流、字体、图片、注释和附件保持一致。
- 签名、加密、损坏文件被拒绝；输出验证失败时不产生最终文件。

### 12.3 M2 强制验收

- 预置样例中的双投标单位名称、项目/标段错误和固定参数矛盾可以定位到双方证据。
- AI 返回虚构锚点、无证据结论或不合规 JSON 时不得成为确定性问题。
- 扫描 PDF 被识别并阻止进入分析流程。
- 相同输入、规则版本和固定 AI 响应产生稳定报告。

### 12.4 M3 强制验收

- 未经用户确认模板范围时不能生成文件。
- DOCX 模板的固定文本、表格结构、样式引用、图片关系和页眉页脚通过结构比对。
- 每个自动填充值都能追溯到招标证据或用户表单。
- 信息不足时保留明确未知项，不生成猜测值。
- 占位符不包含伪造证照、签名或印章。

## 13. 兼容性和演进边界

- Windows x64 与 Linux x64 是首批正式发布目标；其他架构和 macOS 不作为首期发布承诺。
- 报告、任务、AI 输出和 IPC 契约均带版本号；旧报告只读，不做隐式迁移。
- 新 AI 提供商通过 `core/ai` 适配器增加，不能把协议分支散落到业务模块。
- OCR 若以后加入，作为产生带置信度 `DocumentNode` 的独立输入适配器；现有规则和生成模块不直接依赖 OCR 实现。
- 若以后加入本地模型，也复用 AI 契约，不改变文档修改所有权。

- Decision：add-with-proof。

### Product Risk Lens

- Value：减少隐藏信息和人工校对错误，提高资格标模板填充效率。
- Non-goals：替代专业审查、自动投标或规避监管。
- Trade-offs：用户确认步骤增加操作次数，但显著降低误改和 AI 幻觉风险。
- Decision：保留清洗预览、模板确认和填充计划确认三个强制门。

### Architecture Integrity Lens

- Invariant：只有确定性本地引擎能写文件。
- Canonical contracts：版本化 Zod Schema 和统一文档锚点。
- Responsibility overlap：AI、UI 和文档写入明确分离。
- Higher-level simplification：用统一文档模型复用审查和生成的解析能力。
- Falsifier：若具体格式库不能证明未修改非目标部件，则该库不得进入发布路径。
- Verdict：架构边界完整，可进入实施规划。

### Complexity Budget

- Artifact class：Source Complexity 与 Test Complexity。
- Target artifacts：`core/documents`、`core/review`、`core/generation`、`core/ai` 及对应测试夹具。
- Current pressure：空仓库，无历史复杂度。
- Projected pressure：文档格式分支和生成逻辑具有高增长风险。
- Budget result：at-risk。
- Planned governance：每个格式使用独立适配器；解析、规划、写入和验证分离；单一源文件出现混合职责或接近 800 行时优先按所有权拆分。

### Plan-Time Complexity Check

- Better file boundary：以领域所有者和格式适配器分层，不建立通用 `utils` 文档巨型模块。
- Recommendation：按 M0–M4 分解实施计划，每个里程碑单独验证和提交。

## 15. 架构决策信号

以下决策具有长期影响，实施验证后应形成 ADR 或同步到项目架构基线：

- Electron/TypeScript 单体桌面应用与进程边界。
- AI 只产出结构化建议、本地引擎独占文件写入权。
- 统一文档模型与来源锚点是审查和生成的共同契约。
- 原文件只读、签名/加密拒绝、强制验证后落盘。
- OpenAI 兼容适配器是首个协议所有者，其他协议不得侵入业务模块。

这些决策在代码和兼容性测试证明可行之前不记为“已验证完成”。
